================================================================
  SPEAKING SCRIPT — Multi-Document RAG Evaluation Framework
  Target: 10–12 minutes  |  14 slides  |  ~50 sec per slide
================================================================

────────────────────────────────────────────────────────────────
SLIDE 1 — TITLE  (~30 sec)
────────────────────────────────────────────────────────────────

"Today I'm presenting a multi-document RAG evaluation framework
that I built from scratch, grounded in five research papers —
RAG, RankRAG, Self-RAG, MADAM-RAG, and RAGChecker.

The goal was simple: take the best ideas from these papers,
combine them into a single runnable pipeline, and actually
measure what works and what doesn't — with real numbers."


────────────────────────────────────────────────────────────────
SLIDE 2 — THE PROBLEM  (~60 sec)
────────────────────────────────────────────────────────────────

"Let me start with why this problem is hard.

Standard RAG assumes your question can be answered from a single
document. But most real questions aren't like that.

Take this example: 'What is the nationality of the director of
Spectre?' To answer this, you first need to find the Spectre
film article and learn the director is Sam Mendes. Then you need
a second document — Sam Mendes's biography — to find out he's
British. No single document contains the full answer.

And it gets harder. Real corpora also contain adversarial
documents — deliberately wrong information designed to mislead
the model. And even when retrieval works perfectly, LLMs can
still hallucinate — generating plausible-sounding but
completely unsupported claims.

Existing benchmarks evaluate retrieval OR generation — almost
none do both together with proper failure attribution.
That's the gap this project fills."


────────────────────────────────────────────────────────────────
SLIDE 3 — WHAT WE BUILT  (~50 sec)
────────────────────────────────────────────────────────────────

"What I built is three things in one.

First — a benchmark suite. Two datasets, five retrieval methods,
three LLM backends, and over four hundred test queries.

Second — a production pipeline. Every stage from retrieval
through reranking, multi-agent debate, answer extraction, and
faithfulness checking is wired together in one system.

Third — a failure analysis framework. For every wrong answer,
the system tells you exactly why it was wrong — was it a
retrieval failure, a generation failure, or a hallucination?

And across all of this, ten metrics are tracked simultaneously,
so nothing is hidden."


────────────────────────────────────────────────────────────────
SLIDE 4 — RESEARCH FOUNDATION  (~60 sec)
────────────────────────────────────────────────────────────────

"Every component in this pipeline is directly grounded in a
published paper.

RAG from Lewis et al. provides the foundational architecture —
the idea that you retrieve documents first, then generate.

RankRAG from Yu et al. gave me the LLM-as-reranker idea —
instead of just using retrieval scores, ask the LLM to score
each document for relevance.

Self-RAG from Asai et al. inspired the iterative retrieval
method — where you do a second retrieval pass using entities
extracted from the first pass.

MADAM-RAG from Yoran et al. provided the multi-agent debate
framework — one agent per document, then an arbitrator.

And RAGChecker from Ru et al. gave me the faithfulness
evaluation approach and the failure mode taxonomy.

The novel contribution here is integrating all five into one
unified system with a shared schema and common metrics —
something none of these papers did individually."


────────────────────────────────────────────────────────────────
SLIDE 5 — SYSTEM ARCHITECTURE  (~75 sec)
────────────────────────────────────────────────────────────────

"Here's the full pipeline.

A question comes in with a corpus of candidate documents.
It hits the retrieval stage, where one of three methods —
BM25, Hybrid, or Iterative Hybrid — fetches the top K documents.

Those documents go to the LLM reranker, which scores each one
for relevance and reorders them.

The reranked documents enter the multi-agent debate — each
document gets its own agent that produces a local answer and
a confidence score. An arbitrator then picks the final answer.

That answer either goes through rule-based extraction — which
uses regex and pattern matching — or full LLM generation,
depending on the mode.

Finally, the faithfulness checker evaluates whether the answer
is actually grounded in the retrieved documents, and classifies
the failure mode.

Every intermediate result — the ranked IDs, debate turns,
agent outputs, scores — is captured in a unified QueryTrace
object for full reproducibility.

This runs on both HotpotQA and RAMDocs simultaneously."


────────────────────────────────────────────────────────────────
SLIDE 6 — RETRIEVAL METHODS  (~65 sec)
────────────────────────────────────────────────────────────────

"I implemented three retrieval methods with increasing
sophistication.

BM25 is the classic sparse baseline — term frequency matching.
Fast, interpretable, but it misses paraphrases and synonyms.

Hybrid fuses BM25 with dense semantic embeddings using
Reciprocal Rank Fusion. This helps with semantic similarity,
but it's still a single-pass search.

Iterative Hybrid is where it gets interesting. It's inspired by
Self-RAG. First, run the hybrid search on the original question.
Then extract named entities from the results that weren't in the
original question — these are called bridge entities. Then run
a second search with the augmented query.

Going back to the Spectre example: pass one retrieves the Spectre
article. Bridge entity extraction pulls out 'Sam Mendes'.
Pass two retrieves the Sam Mendes biography. Now both gold
documents are in the result set. That's something a single-pass
retriever can never do reliably."


────────────────────────────────────────────────────────────────
SLIDE 7 — RERANKING & DEBATE  (~65 sec)
────────────────────────────────────────────────────────────────

"After retrieval, documents go through two stages.

The LLM reranker — inspired by RankRAG — asks the model to score
each document from 1 to 10 for relevance to the question.
Documents are reordered by that score before entering the debate.
If the LLM call fails, the original retrieval order is used as
fallback — the system never stops.

Then the multi-agent debate from MADAM-RAG. Each retrieved
document gets its own agent. The agent reads its document,
produces a local answer, and attaches a confidence score.

Here's the key mechanism for misinformation suppression:
each document carries a label — gold, misinformation, or noise.
Gold documents get a multiplier of plus two. Misinformation
documents get minus one point five. Noise gets minus zero point
five.

The arbitrator aggregates weighted votes and picks the answer
with the highest total weight. This actively suppresses
adversarial documents — it's not just observational.

On RAMDocs, this achieved 96.5% misinformation suppression."


────────────────────────────────────────────────────────────────
SLIDE 8 — FAITHFULNESS CHECKING  (~55 sec)
────────────────────────────────────────────────────────────────

"Faithfulness checking has two paths — and it always produces
a result regardless of LLM availability.

Path A is the LLM judge, modeled after RAGChecker. It receives
the question, the predicted answer, the gold answer, and the
retrieved documents. It returns three things: a faithfulness
score from 0 to 10, a list of specific hallucinated claims,
and a failure mode classification.

Path B is the deterministic fallback. Pure logic: if exact match
is correct, it's 'correct'. If exact match fails but the gold
documents were retrieved, it's a 'generation failure' — the
model had the right information but still got it wrong. If the
gold documents weren't retrieved, it's a 'retrieval failure'.

The most important finding from this analysis: 90% of all
failures are retrieval failures. Only about 10% are generation
failures. The ratio is nine to one. That tells you exactly where
to focus your engineering effort."


────────────────────────────────────────────────────────────────
SLIDE 9 — EXPERIMENTAL SETUP  (~45 sec)
────────────────────────────────────────────────────────────────

"I ran four experimental configurations to isolate different
pipeline stages.

The baseline establishes the floor — no LLM reranker, rule-based
extraction, deterministic faithfulness.

The LLM Rerank run adds a Groq 8B reranker to measure the
impact of reranking alone.

The Haiku Best run uses Claude Haiku — the highest quality
backend — to measure the ceiling.

And the LLM Generation run switches to full LLM debate
synthesis to see whether generating answers rather than
extracting them helps or hurts.

Each run processed 200 HotpotQA queries and 200 RAMDocs queries,
with roughly three thousand LLM calls per complete run."


────────────────────────────────────────────────────────────────
SLIDE 10 — RESULTS: RETRIEVAL QUALITY  (~55 sec)
────────────────────────────────────────────────────────────────

"Let's look at retrieval quality on HotpotQA.

The baseline BM25 with no reranker gets a Recall at 5 of 0.650
and an MRR of 0.850.

Adding the LLM reranker to BM25 immediately jumps Recall to
0.750 — that's a fifteen percent improvement from one component.

Hybrid retrieval with the reranker brings it to 0.768.

And Iterative Hybrid hits 0.770 with an MRR of 0.926 — the
best across the board.

The multi-doc hit rate — which measures whether ALL gold
documents for a multi-hop question are in the top K — also
improves progressively. Iterative Hybrid reaches 0.435 versus
the baseline's 0.245.

This confirms the hypothesis: two-pass retrieval with bridge
entity extraction is genuinely better for multi-hop questions,
not just marginally better."


────────────────────────────────────────────────────────────────
SLIDE 11 — RESULTS: ANSWER QUALITY  (~65 sec)
────────────────────────────────────────────────────────────────

"Now the answer quality results — and these are where things
get really interesting.

The baseline BM25 gets an exact match of 0.595.

Adding the LLM reranker jumps it to 0.74 — a 24% improvement.

The best single configuration is Haiku as reranker with
rule-based extraction, hitting 0.800 exact match with zero
hallucination rate on HotpotQA. That's the ceiling.

Now look at the LLM generation rows. When I switched to full
LLM debate synthesis, exact match dropped to 0.22 for BM25 —
from 0.80 to 0.22. That looks catastrophic.

But it's actually a measurement artifact. The LLMs are often
correct — they say 'British nationality' or 'from the United
Kingdom' when the gold answer is just 'British'. Exact match
penalizes valid paraphrases. That's why faithfulness scores
and F1 scores tell a different story — Iterative Hybrid in
LLM generation mode actually achieves the best faithfulness
of 0.574.

On RAMDocs, exact match is consistently around 0.96 across
all methods, confirming the debate mechanism works."


────────────────────────────────────────────────────────────────
SLIDE 12 — LLM BACKEND COMPARISON  (~55 sec)
────────────────────────────────────────────────────────────────

"I compared three LLM backends on the same pipeline.

Ollama with Llama 3.2 3B runs fully locally — no API, no cost,
no data leaving your machine. But reranking quality is weak,
and exact match barely exceeds the no-reranker baseline at 0.650.

Groq with Llama 3.1 8B is the free cloud tier. Significantly
stronger reranker — exact match of 0.74, and on the LLM
generation run with Iterative Hybrid, it achieves the best
faithfulness score of 0.574 with only 18% hallucination rate.
The downside is the free tier rate limit of 30 requests per
minute, which turned a run into a 3.5 hour job.

Claude Haiku is the clear winner on answer quality — 0.800
exact match, fastest response time, and zero hallucinations
in the rule-based configuration. It costs money but delivers
measurably better reranking.

The practical conclusion: if quality matters, pay for Haiku.
If cost matters, Groq gets you most of the way there for free."


────────────────────────────────────────────────────────────────
SLIDE 13 — KEY INSIGHTS  (~60 sec)
────────────────────────────────────────────────────────────────

"Four key insights from all of this.

First — 9 to 1. Nine out of ten wrong answers are retrieval
failures, not hallucinations. The model had no chance of getting
it right because the right documents were never in the context.
This means retrieval engineering should get the majority of your
optimization budget — not prompt tuning.

Second — the LLM reranker was the single highest-impact
component. One component added to the baseline took exact match
from 0.595 to 0.800. That's a larger gain than any retrieval
method improvement.

Third — LLM generation actually hurts exact match. It dropped
from 0.80 to 0.22. Rule-based extraction is better for factoid
questions. This is a strong argument for keeping extraction
deterministic and using LLMs only for reranking.

Fourth — misinformation suppression works at 96.5%. The
label-weighted voting in MADAM-RAG actively blocks adversarial
documents, not just passively. This is a real mechanism, not a
side effect."


────────────────────────────────────────────────────────────────
SLIDE 14 — CONCLUSION  (~40 sec)
────────────────────────────────────────────────────────────────

"To summarize what this project delivered.

I built a complete multi-document RAG pipeline combining five
research papers, benchmarked across 400 queries and three LLM
backends, with full failure mode analysis at every step.

The best configuration — Iterative Hybrid retrieval with a
Claude Haiku reranker and rule-based extraction — achieves
an exact match of 0.800 on HotpotQA and 96.5% misinformation
suppression on RAMDocs.

The core finding is that retrieval quality dominates everything
else. Better retrieval beats better generation. And a strong
LLM reranker is the single most cost-effective improvement
you can make to a multi-document RAG system.

I'm happy to take questions."

================================================================
LIKELY PROFESSOR QUESTIONS — prepared answers
================================================================

Q: "Why does exact match drop so much with LLM generation?"
A: Exact match penalizes valid paraphrases. An LLM says
   "British nationality" and the gold is "British" — EM = 0.
   F1 and faithfulness tell a more accurate story. EM is a
   useful proxy for factoid QA but not a complete picture.

Q: "Are the RAMDocs labels realistic? Don't you need oracle info?"
A: Great question. Our implementation uses oracle labels from
   the dataset — that's an honest limitation. The original
   MADAM-RAG paper designs agents to discover misinformation
   through disagreement patterns without labels. Our version
   is a label-supervised approximation that demonstrates
   the mechanism works, but a real deployment would need
   label-free detection.

Q: "What would you improve next?"
A: Three things: (1) replace oracle labels with LLM-based
   misinformation detection to make it label-free,
   (2) use F1 or semantic similarity as the evaluation metric
   instead of EM for LLM generation mode,
   (3) test on larger corpora — current runs use 10 docs per
   query which is small compared to production RAG systems.

Q: "Why is Iterative Hybrid not the best on answer EM?"
A: Iterative Hybrid wins on retrieval metrics but the answer
   EM is close across methods (0.74 vs 0.705) because the
   bottleneck shifts to the reranker and extraction stage once
   retrieval is good enough. The reranker quality (Haiku vs
   Groq) matters more than the retrieval method at that point.

Q: "How does this compare to published MADAM-RAG results?"
A: The original MADAM-RAG paper reports results on their full
   setup. Our system is a research scaffold, not a replication.
   The meaningful comparison is internal — showing the relative
   improvement of each component within our pipeline — rather
   than claiming to beat the original paper's numbers.
