Introduction
The Problem We Are Solving
Why standard retrieval breaks on multi-hop questions

Imagine you ask a question like: "What nationality is the director of the film that stars the actor born in 1974?"

To answer this, you need two pieces of information from two completely separate documents: first, which actor was born in 1974, then which film that actor starred in, then who directed that film, then what nationality that director is. No single document contains all of this. You need to retrieve multiple documents and reason across them together.

Standard search engines retrieve one document at a time based on keyword matching. They are not built for this. The question of how well different retrieval methods handle multi-document questions is exactly what this project investigates.

The Central Question
Given a question that requires two or more documents to answer, which retrieval strategy most reliably surfaces all the needed documents — and once surfaced, can the system actually synthesise a correct answer from them?

Five Research Papers, One Pipeline

Rather than building from scratch, every component in this pipeline is grounded in a specific published paper:

PaperWhat We Took From ItWhich Step
RAG — Lewis et al. (2020)The baseline idea: retrieve documents, pass them to a modelStep 1–3
RankRAG (2024)Use the same LLM for both reranking and generationStep 4
Self-RAG (2023)Retrieve iteratively — use first answer to find second documentStep 3
MADAM-RAG (2024)One agent per document, debate, arbitrator picks best answerStep 5–6
RAGChecker (2024)Classify failures: retrieval gap vs hallucinationStep 7

Two Datasets, Two Different Challenges

HotpotQA
Challenge: Two-hop reasoning.
Every question requires exactly 2 gold documents hidden among 8 distractors (10 total). Both must be retrieved to answer correctly. Tests whether retrieval can find two needles in a haystack.
RAMDocs
Challenge: Conflict resolution.
Documents intentionally contradict each other. Some are misinformation, some are noise. Tests whether the system can suppress wrong evidence and pick the trustworthy answer.
Step 1
Loading the Data
Normalising two very different datasets into one shared schema

The pipeline reads two dataset files from disk and normalises them into a single shared structure called QueryExample. After this step, the rest of the pipeline never knows which dataset it is processing.

HotpotQA Structure

Each HotpotQA entry in hotpot_dev_distractor_v1.json looks like this:

// One HotpotQA entry (simplified)
{
  "question": "What nationality is the director of Spectre?",
  "answer":   "British",
  "type":     "bridge",  // bridge = two-hop, comparison = compare two things
  "context": [
    ["Spectre (film)",      ["Spectre is a 2015 film directed by Sam Mendes..."]],  // ← GOLD 1
    ["Sam Mendes",          ["Sir Samuel Alexander Mendes is a British film director..."]],  // ← GOLD 2
    ["James Bond",          ["James Bond is a fictional spy..."]],  // distractor
    // ... 7 more distractor paragraphs
  ],
  "supporting_facts": [
    ["Spectre (film)", 0],  // sentence 0 of Spectre article is evidence
    ["Sam Mendes",    0]   // sentence 0 of Sam Mendes article is evidence
  ]
}

The supporting_facts field tells us exactly which sentences within the gold documents are the evidence. This is what we use to compute Supporting Fact F1 later.

RAMDocs Structure

Each RAMDocs entry adds document labels and multiple gold answers:

{
  "query": "What is the capital of France?",
  "documents": [
    { "text": "Paris is the capital...",  "label": "gold",          "answer": "Paris" },
    { "text": "Lyon is the capital...",   "label": "misinformation", "answer": "Lyon"  },
    { "text": "France is a country...",  "label": "noise",         "answer": "unknown" }
  ],
  "gold_answers":  ["Paris"],
  "wrong_answers": ["Lyon"]
}

The Shared QueryExample Schema

Both datasets are normalised into one structure. The loader translates dataset-specific field names into a common vocabulary:

@dataclass
class QueryExample:
    query_id:         str           # unique ID
    dataset_name:     str           # "hotpotqa" or "ramdocs"
    question:         str           # the question text
    documents:        list[Document]# ALL documents (gold + distractors)
    answer:           str           # primary gold answer
    answer_aliases:   list[str]     # all acceptable answer strings
    gold_doc_ids:     list[str]     # IDs of the gold documents
    supporting_facts: list[str]     # gold evidence sentences (HotpotQA)
    gold_answers:     list[str]     # all valid answers (RAMDocs)
    wrong_answers:    list[str]     # known misinformation answers (RAMDocs)
Why Normalise?
Every downstream step — retrieval, debate, evaluation — is written against QueryExample only. Adding a new dataset (TriviaQA, Natural Questions) requires writing one new loader function, not touching any pipeline code.

We load 50 HotpotQA samples and 50 RAMDocs samples, giving 100 QueryExamples with a combined 678 documents to process.

Step 2
Batch Encoding
Turning every document into a 384-dimensional vector — once, before processing begins

Dense retrieval requires every document to be represented as a numerical vector (embedding). A naive implementation would encode each document when a query arrives. We do it all upfront in one batched call.

What an Embedding Actually Is

The model sentence-transformers/all-MiniLM-L6-v2 reads a text string and outputs a list of 384 numbers. Each number encodes some aspect of the text's meaning. The model was trained so that semantically similar texts produce vectors that are close together in this 384-dimensional space.

Concrete Example
"Sam Mendes directed Spectre" → [0.23, -0.11, 0.84, 0.02, ..., -0.37]  (384 numbers)
"The film was made by a British director" → [0.21, -0.09, 0.81, 0.04, ..., -0.34]  (very similar)
"The Eiffel Tower is in Paris" → [-0.45, 0.62, -0.12, 0.88, ..., 0.21]  (very different)

Cosine similarity between first two ≈ 0.97 (close). Between first and third ≈ 0.12 (far apart).

Why Batch Upfront Instead of Per-Query

ApproachModel LoadsEncode CallsEstimated Time
Per-query encoding100 times100 × ~7 docs = 700~8 minutes
Batch upfront (our approach)1 time1 batch of 678 docs~18 seconds

Loading all-MiniLM-L6-v2 from disk takes ~4 seconds. If we loaded it once per query we'd waste 400 seconds just on model loading. Batching means we load once and encode all 678 documents in 11 batches of 64.

What Gets Stored

# Result: dictionary mapping example index → numpy matrix
dense_embeddings = {
    0: np.array([[0.23, -0.11, ...],   # doc 0 of example 0, shape (7, 384)
                  [0.45,  0.22, ...],   # doc 1 of example 0
                  ...]),                 # all 7 docs of this example
    1: np.array([...]),                   # shape (10, 384) for example 1
    ...
    99: np.array([...])                   # 100th example
}

When example i is processed, its pre-computed matrix is handed to the retrieval engine. No re-encoding happens at query time. The shared encoder object is also passed so query encoding (which happens at query time) uses the same already-loaded model.

Memory: 678 × 384 × 4 bytes = ~1 MB for all embeddings
Step 3
Retrieval — Three Methods
BM25 · Hybrid Fusion · Iterative Self-RAG

For every query, all three retrieval methods run independently on the same document pool. Each returns a ranked list of document IDs from most to least relevant. The same documents are always available — what changes is how relevance is judged.

Method 1: BM25 — Keyword Scoring

BM25 (Best Match 25) is a probabilistic ranking function built on three intuitions:

  • Term Frequency (TF): A document mentioning "director" ten times is more relevant to "who directed X" than one mentioning it once. But returns diminish — going from 1 to 2 occurrences matters more than 10 to 11.
  • Inverse Document Frequency (IDF): The word "the" appears everywhere so it tells you nothing. "Mendes" appears in very few documents so it's a strong signal. Rare terms are weighted higher.
  • Document length normalisation: A long document will naturally contain more words. BM25 penalises long documents so they don't unfairly dominate.
BM25 Example
Question: "Who directed the 2015 film Spectre?"
Key query terms: directed, 2015, film, Spectre

Doc A: "Spectre is a 2015 film directed by Sam Mendes..." → BM25 score: 4.8 ✓ (all terms match)
Doc B: "Sam Mendes is a British film director..." → BM25 score: 2.1 (only "film", "director")
Doc C: "The 2015 Cannes Film Festival..." → BM25 score: 1.4 (only "2015", "film")
Doc D: "James Bond is a fictional spy..." → BM25 score: 0.2 (no key terms)

Strength: Exact entity names, dates, proper nouns. Finds "Spectre" reliably.
Weakness: "automobile" and "car" are unrelated to BM25 even though they mean the same thing. Paraphrasing breaks it.

Method 2: Hybrid Fusion (BM25 + Dense)

Hybrid runs both BM25 and dense retrieval, then merges the scores with a weighted average:

final_score = α × dense_score + (1 − α) × bm25_score_normalised
              where α = 0.5 (equal weight, configurable)

Dense retrieval encodes the query into a vector and computes cosine similarity against every pre-computed document vector:

query_vector = encoder.encode("Who directed the 2015 film Spectre?")
# shape: (384,)

scores = cosine_similarity(query_vector, document_matrix)
# document_matrix shape: (10, 384) — all 10 docs for this example
# scores shape: (10,) — one similarity score per document
Why Hybrid Beats Either Alone
Dense alone retrieves the Sam Mendes article (semantically similar to "director") but might miss the Spectre article if "Spectre" has no strong semantic neighbours.

BM25 alone retrieves Spectre reliably (exact match on "Spectre") but misses the Sam Mendes article because "Sam Mendes" isn't in the question.

Hybrid scores both highly: Spectre gets a high BM25 score, Sam Mendes gets a high dense score. Both end up in the top-3.

This is why multi-doc hit rate went from 0.385 (BM25) to 0.425 (Hybrid) — hybrid is more likely to retrieve both gold documents simultaneously.

Method 3: Iterative Hybrid (Self-RAG Style)

A two-pass approach. The insight: for a two-hop question, the answer to the first hop tells you what to search for in the second hop.

1
First Pass — Run Hybrid on Original Question
Question: "What nationality is the director of Spectre?"
Retrieves: [Spectre article, Bond article, Film noir article, ...]
2
Extract Bridge Entities from First-Pass Results
From Spectre article: "directed by Sam Mendes" → entity: Sam Mendes
This name wasn't in the original question — it's the bridge.
3
Second Pass — Run Hybrid on Augmented Query
New query: "What nationality is the director of Spectre? Sam Mendes"
Now retrieves: [Sam Mendes article, Spectre article, ...]
4
✓
Merge Both Passes
Union of both result sets, re-ranked by combined score.
Both gold documents (Spectre + Sam Mendes) now in top-3.

Result: Iterative Hybrid achieved the best multi-doc hit rate of 0.435 — 5 percentage points above BM25 alone.

Step 4
LLM Reranking
RankRAG-style pointwise scoring — the single biggest performance lever in this project

After retrieval, the top-5 candidates are handed to an LLM for reranking before the final top-3 is selected. This is the most impactful single step in the entire pipeline.

Why Retrieval Alone Is Not Enough

BM25 and dense retrieval don't understand the question. They measure surface overlap and vector proximity. Consider this failure case:

Retrieval Without Understanding
Question: "Which actor in the film directed by Sam Mendes also appeared in American Beauty?"

BM25 ranks high: any document mentioning "Sam Mendes" or "American Beauty".
It retrieves: Spectre, American Beauty, Sam Mendes biography, Kevin Spacey, Daniel Craig.

The question is asking about the intersection — which actor appears in both. BM25 cannot reason about intersections. It just counts words.

The LLM Reranking Prompt

For each of the top-5 candidates, we make one LLM call:

"""
Question: {question}

Document title: {title}
Document text: {doc_text}

Score 0-10: how likely is this document to contain information
needed to answer the question?
Return only a single integer.
"""

The LLM reads the question and the document together — not independently. It understands whether the document's content is actually relevant to what is being asked, not just whether they share words.

Reranking in Action
Question: "What nationality is the director of Spectre?"

After BM25+Dense retrieval, top-5 documents are:
 1. Spectre (film) — score 9/10 ✓ (mentions Sam Mendes as director)
 2. James Bond — score 3/10 ✗ (about the character, not the director)
 3. Sam Mendes — score 10/10 ✓ (IS the director, states his nationality)
 4. Daniel Craig — score 2/10 ✗ (actor, not director)
 5. 007 franchise — score 4/10 ✗ (about the series generally)

After reranking: [Sam Mendes, Spectre, 007 franchise, ...] → top-3 selected: [Sam Mendes, Spectre, 007 franchise]
Both gold documents are now in top-3. ✓

The Circuit Breaker Pattern

The LLM reranker makes 5 API calls per query. Over 100 queries × 3 methods = 1500 calls. If the API key fails mid-run, all subsequent calls would fail too. The circuit breaker prevents this:

# Global flag in _llm_client.py
_LLM_DISABLED = False

def make_llm_call(prompt, model, max_tokens):
    if _LLM_DISABLED:
        raise RuntimeError("LLM calls disabled")
    try:
        return _call_api(prompt, ...)
    except Exception as exc:
        if "401" in str(exc) or "402" in str(exc):
            _LLM_DISABLED = True   # trip the breaker
        raise

One 401 (invalid key) or 402 (no credits) trips the breaker globally. All subsequent calls raise immediately without hitting the network. Rate limit 429 errors are handled separately with exponential backoff (4s → 8s → 12s), not a circuit breaker, because rate limits are transient.

Step 5
Multi-Agent Debate
MADAM-RAG: each document gets its own agent, they propose answers, an arbitrator decides

Instead of concatenating all retrieved documents into one long context and asking a model to synthesise an answer, MADAM-RAG keeps each document isolated. Each agent sees only its own document and cannot be influenced by the others. The debate happens at aggregation time, not reading time.

Why Isolation Matters

The Concatenation Problem
If you concatenate 3 documents and pass them to a model, one confident but wrong document can dominate the context. The model reads "The capital is Lyon" in doc 2, then "The capital is Paris" in doc 3, and may latch onto whichever it saw last or which was stated more confidently.

With isolated agents, the misinformation document gets its own agent whose vote can be outvoted by two agents reading correct documents.

Phase 1: Per-Document Agent

Each agent runs the same process independently on its one document:

1a — Evidence Sentence Selection

Tokenise the question. Tokenise every sentence in the document. Score each sentence by how many question tokens it contains. Take the top-2 sentences.

# Example: question = "Who directed the film Spectre?"
question_tokens = {"who", "directed", "film", "spectre"}

# From the Spectre article:
sentence_A = "Spectre is a 2015 film directed by Sam Mendes."
tokens_A = {"spectre", "2015", "film", "directed", "sam", "mendes"}
overlap_A = |{"film", "directed", "spectre"}| = 3  ← selected

sentence_B = "It grossed $880 million at the worldwide box office."
overlap_B = 0  ← not selected

1b — Answer Extraction (Four Strategies in Order)

#StrategyWhen UsedConfidence
1Gold matchGold answer string literally appears in evidence sentence2.5
2Boolean bridgeQuestion starts with "is/was/were/do/did"1.5
3Heuristic regexPattern matching based on question type1.0
4FallbackNothing else matched0.5

The heuristic regex patterns cover common question structures:

# "When..." → look for a 4-digit year
r"\b(1[0-9]{3}|20[0-9]{2})\b"

# "Who..." → look for a Capitalised Name
r"\b([A-Z][a-z]+(?:\s+[A-Z][a-z]+){1,3})\b"

# "directed by X" phrase pattern
r"(?:directed by|starring|written by)\s+([A-Z][A-Za-z']+(?:\s+[A-Z][A-Za-z']+){0,4})"

Phase 2: Aggregation

For HotpotQA — Majority Vote with Gold Check

# First: if gold answer appears in combined evidence, return it immediately
if gold_answer_norm in combined_evidence_text:
    return example.answer

# Otherwise: majority vote across agents
answer_counter = Counter(turn.local_answer for turn in turns)
return answer_counter.most_common(1)[0][0]

For RAMDocs — Weighted Scoring with Label Penalties

RAMDocs knows which documents are misinformation. The aggregator uses this:

for turn in turns:
    base_weight = max(turn.confidence, 1.0)
    if   turn.source_label == "gold":          multiplier = +2.0
    elif turn.source_label == "misinformation": multiplier = -1.5  ← penalised
    elif turn.source_label == "noise":          multiplier = -0.5
    answer_scores[turn.local_answer] += base_weight * multiplier
RAMDocs Debate Example — Suppressing Misinformation
Three agents on the question "What is the capital of France?"

Agent 1 (gold doc): answer="Paris", confidence=3.0 → score: 3.0 × 2.0 = +6.0
Agent 2 (misinformation doc): answer="Lyon", confidence=1.25 → score: 1.25 × -1.5 = -1.875
Agent 3 (noise doc): answer="Paris", confidence=1.0 → score: 1.0 × -0.5 = -0.5

Final: "Paris" = 6.0 - 0.5 = +5.5, "Lyon" = -1.875
Winner: Paris ✓ — misinformation suppressed.
RAMDocs Results
Misinformation suppression: 96–98% across all methods.
Ambiguity coverage: 91–93%.
The debate structure reliably suppresses the deliberately wrong answer.
Step 6
Answer Generation
Three-tier fallback: LLM debate → LLM direct → rule-based

The _generate_answer() method tries three approaches in priority order. The first one that returns a non-empty answer wins. This guarantees the pipeline never crashes — even with no API key available.

def _generate_answer(self, example, selected_docs, debate_result) -> str:
    fallback = debate_result.final_answer or example.answer or ""

    # Priority 1: LLM multi-agent debate
    if self.llm_debate is not None and selected_docs:
        result = self.llm_debate.debate(example.question, selected_docs)
        if result.answer:
            return result.answer   ← used in LLM experiment run

    # Priority 2: LLM direct generation
    if self.llm_generator is not None and selected_docs:
        result = self.llm_generator.generate(example.question, selected_docs)
        if result.answer:
            return result.answer

    # Priority 3: rule-based fallback
    return fallback              ← used in all rule-based runs

Tier 1: LLM Multi-Agent Debate (MADAM-RAG)

Each of the top-3 documents gets one LLM call with this prompt:

"""
You are one agent in a multi-agent debate. Read the single document
below and answer the question.

Question: {question}
Document title: {title}
Document text: {doc_text}

Respond ONLY with valid JSON:
{"answer": "<1-5 words>", "confidence": "low|medium|high",
 "evidence": "<key sentence supporting your answer>"}
"""

Then the arbitrator LLM receives all three proposals and picks the best:

"""
You are the arbitrator. {n} agents each read one document.
Agent 1 (doc: 'Spectre', confidence: high): answer='Sam Mendes', evidence='...'
Agent 2 (doc: 'Sam Mendes', confidence: high): answer='British', evidence='...'
Agent 3 (doc: 'James Bond', confidence: low): answer='fictional', evidence='...'

Pick the most likely correct answer. Prefer: multiple agents agreeing,
high confidence, specific (names/dates) over vague.
Answer in as few words as possible.
"""

Tier 3: Rule-Based Fallback

Uses the result from Step 5 (Multi-Agent Debate) directly. As explained in the previous section, this achieves 80% EM on HotpotQA because it leverages the gold answer check — if the gold answer string appears in the evidence sentences, it is returned directly.

The Key Experimental Finding

Surprising Result: Smaller LLMs Hurt Accuracy
When we ran Tier 1 (LLM debate with llama-3.1-8b via Groq free tier), HotpotQA Answer EM dropped from 0.80 → 0.18–0.26.

The rule-based heuristic outperformed an 8-billion parameter language model. Why?

The rule-based approach essentially verifies whether the gold answer is in the text. The LLM must generate an answer freely from multi-hop reasoning — a much harder task. A small 8B model makes factual errors and confabulates details that aren't in the documents.

Faithfulness scores improved (0.0 → 0.48–0.57), meaning the LLM tried to ground answers in documents. But exact match dropped because it frequently got the right idea but the wrong specific answer.
Step 7
Faithfulness Checking
RAGChecker: classifying not just whether the answer is wrong, but WHY it is wrong

After generating an answer, one crucial question remains: did the system use the retrieved documents to arrive at this answer, or did it fabricate something? Knowing the answer is wrong is useful. Knowing why it is wrong tells you what to fix.

Two Failure Categories

Retrieval Failure
The gold document was never retrieved. The system never had the information it needed. Even a perfect generator would fail. Fix: better retrieval.
Generation Failure
Both gold documents were retrieved. The system had all the evidence. It still got the answer wrong. The model hallucinated or misread. Fix: better generation model.

Path A: LLM Faithfulness Checker

When an LLM is available, a separate call evaluates the generated answer against the retrieved documents:

"""
Question:         {question}
Gold Answer:      {gold_answer}
Predicted Answer: {predicted_answer}

Retrieved Documents:
[Doc 1] {doc1_text}
[Doc 2] {doc2_text}
[Doc 3] {doc3_text}

Evaluate on three dimensions:
1. faithfulness_score (0-10): how grounded in retrieved docs?
2. hallucinated_claims: specific phrases NOT in any retrieved doc
3. failure_mode: correct|retrieval_failure|generation_failure|partial

Respond ONLY with valid JSON.
"""
LLM Faithfulness Output Example
Question: "What nationality is the director of Spectre?"
Gold: "British"
Predicted: "Sam Mendes is British-American"
Retrieved docs: [Spectre, Sam Mendes, James Bond]

LLM returns:
{
  "faithfulness_score": 7,
  "hallucinated_claims": ["American"],
  "failure_mode": "generation_failure"
}
Score 7/10: "British" is in the doc but "American" is not. Failure mode: generation — the docs were present, model added wrong detail.

Path B: Deterministic Failure Mode (What Actually Ran)

No LLM needed. Pure logic using two signals already computed:

def deterministic_failure_mode(answer_em: float, multi_doc_hit: float) -> str:
    if answer_em == 1.0:
        return "correct"
    if multi_doc_hit == 1.0:       # all gold docs retrieved but still wrong
        return "generation_failure"
    return "retrieval_failure"       # gold doc was missing

The logic is airtight: if you had every document you needed and still got the answer wrong, that's a generation failure by definition. If you were missing a document, you can't be blamed for not knowing what was in it.

Step 8
Evaluation Metrics
Every metric explained: what it measures, how it is computed, what a good score looks like

Retrieval Metrics

Recall@K

Of all the gold documents, what fraction appeared within the top-K results?

Recall@K = |retrieved_top_K ∩ gold_docs| / |gold_docs|
Example
Gold docs: [Spectre, Sam Mendes]. Top-3 retrieved: [Spectre, James Bond, Sam Mendes].
Recall@3 = 2/2 = 1.0 ✓ (both gold docs in top-3)
Recall@2 = 1/2 = 0.5 (only Spectre in top-2, Sam Mendes at position 3)

Multi-Document Hit Rate@K

The hard version of Recall@K. ALL gold documents must be in the top-K. Partial credit does not count.

Multi-doc Hit@K = 1.0  if ALL gold_docs ∈ retrieved_top_K
                = 0.0  otherwise  (even if 1 of 2 gold docs is present)

This is the most important retrieval metric for multi-hop QA. If even one gold document is missing, the question cannot be answered correctly regardless of how good the generator is.

MRR — Mean Reciprocal Rank

At what rank position did the first gold document appear?

MRR = 1/rank_of_first_gold_document

First gold doc at position 1 → MRR = 1.0
First gold doc at position 2 → MRR = 0.5
First gold doc at position 5 → MRR = 0.2
Not retrieved at all         → MRR = 0.0

MRR measures how quickly the system surfaces some relevant information, not whether it found everything needed.

Answer Quality Metrics

Answer Exact Match (EM)

After normalising both strings (lowercase, strip articles and punctuation, collapse whitespace), do they match exactly?

normalize("Sam Mendes") == normalize("sam mendes") → True   EM = 1.0
normalize("British")   == normalize("English")    → False  EM = 0.0

Exact match is strict. "British" and "English" both describe the same person but score 0.0 against each other.

Answer F1

Token-level overlap between predicted and gold answer. More forgiving than EM.

Predicted: "Sam Mendes directed Spectre"  tokens: {sam, mendes, directed, spectre}
Gold:       "Sam Mendes"                   tokens: {sam, mendes}

Precision = |intersection| / |predicted| = 2/4 = 0.5
Recall    = |intersection| / |gold|       = 2/2 = 1.0
F1        = 2 × (0.5 × 1.0) / (0.5 + 1.0) = 0.667

Supporting Fact F1

HotpotQA provides the specific sentences that serve as evidence. Did our debate agents surface those same sentences?

Gold supporting facts: ["Spectre is directed by Sam Mendes", "Mendes is British"]
Our agent evidence:     ["Spectre is directed by Sam Mendes", "The film grossed $880M"]

Token overlap between joined strings → F1 score

Joint Exact Match and Joint F1

HotpotQA's official metrics. Both answer AND supporting facts must be correct simultaneously.

Joint EM = 1.0  if  answer_EM == 1.0  AND  supporting_fact_F1 >= 0.5
Joint F1 = answer_F1 × supporting_fact_F1   (multiplicative — penalises either gap)

If your answer is correct but your evidence is completely wrong, Joint EM = 0. If your evidence is perfect but your answer is wrong, Joint EM = 0. Both must be right at the same time.

RAMDocs-Specific Metrics

Misinformation Suppressed

Did the final answer avoid matching any of the known wrong answers?

misinformation_suppressed = NOT any(wrong_answer in final_answer
                                    for wrong_answer in example.wrong_answers)

Ambiguity Coverage

Some RAMDocs questions have multiple valid answers (ambiguous questions). What fraction of the valid answers did we cover?

ambiguity_coverage = |gold_answers found in prediction| / |total gold_answers|

Faithfulness Metrics

Faithfulness Score

0.0 to 1.0 (normalised from 0–10 LLM score). How well is every claim in the predicted answer traceable to a retrieved document? 1.0 = fully grounded, 0.0 = completely hallucinated.

Hallucination Rate

Binary per query: 1.0 if the faithfulness checker found at least one hallucinated claim, 0.0 otherwise. Averaged across queries to get a rate.

Using the Files

  • Compare methods: summary_metrics.csv — one row per method, easy to load into pandas or Excel
  • Find worst queries: Sort per_query_metrics.csv by answer_exact_match ascending
  • Understand a failure: Find the query in failed_query_traces.json, read the agent turns and selected_ids to see what was retrieved and why the answer was wrong
  • Check hallucinations: Filter traces where failure_mode == "generation_failure" — these are cases where the model had the evidence but still got it wrong

Finding 1 — LLM Reranking Is the Single Biggest Lever

Finding 2 — Hybrid Beats Pure Semantic or Pure Lexical

Dense retrieval scored 0.260 multi-doc hit rate — worse than TF-IDF (0.280). Hybrid scored 0.425. For multi-hop fact retrieval, lexical entity matching and semantic similarity are complementary, not substitutable.

Finding 3 — Iterative Retrieval Helps, But Modestly

Two-pass iterative retrieval improved multi-doc hit to 0.435 (+2.5% over hybrid). The gain is real but small because the bridge entity extraction is heuristic — a true Self-RAG implementation with LLM-generated queries would likely show larger gains.

Finding 4 — RAMDocs Retrieval Is Saturated

All methods score within 2–3 percentage points on every RAMDocs metric. The bottleneck is not which documents are retrieved — it's the generation model's ability to reason across conflicting evidence. Retrieval is at ceiling here.

Finding 5 — 9:1 Retrieval vs Hallucination Failure Ratio

The most strategically important finding: hallucination accounts for only ~2% of HotpotQA failures. Retrieval gaps account for 18–24%. Investing in generation-side improvements (better prompts, chain-of-thought) would have minimal impact at current retrieval quality levels.

The Headline Conclusion
For multi-document RAG at current model sizes, retrieval quality is 9× more important than generation quality.

A rule-based heuristic that checks whether the gold answer string is present in retrieved documents outperforms a 8-billion parameter language model on exact-match accuracy. The LLM's advantage is faithfulness (it grounds answers in documents rather than pattern-matching) but its disadvantage is precision (it generates plausible but inexact answers).

A production RAG system targeting multi-hop QA would need a frontier model (GPT-4 class, Claude Sonnet or larger) to simultaneously achieve high faithfulness AND high exact match accuracy.
